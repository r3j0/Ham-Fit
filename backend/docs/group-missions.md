# 그룹 미션·룰렛

2026-09-30 사용자 확정 정책을 구현했다. 2026-09-29 문서의 미정 정책과 ‘그룹 미션 미구현·개인 재화 미연결’ 설명을 이 문서로 대체한다. 물은 일별 운동 성공의 그룹 성장 기여 단위다. 룰렛이 지급하는 해바라기씨는 기존 개인 `UserCurrency`이며 그룹 지갑이나 별도 개인 잔액을 만들지 않는다.

## 회차와 참여 자격

- 현재 그룹장이 시작 API를 호출한다. 그룹장 포함 현재 구성원 최소 2명이 필요하다. 그룹 생성은 기존처럼 1명이어도 가능하다.
- 시작 트랜잭션에서 구성원 전체와 실제 인원 N을 저장한다. 목표는 누적 14N이며 정원이 아니다. 진행 중 회차는 그룹당 하나다.
- 자동/예약 시작, 기한, 중단, 포기, 초기화는 없다. 완료 후 다음 회차도 그룹장이 직접 시작한다. 그룹장 변경과 구성원이 1명으로 줄어드는 경우에도 진행 회차를 유지한다.
- 시작 후 가입자는 해당 회차에 참여하거나 보상받지 않는다. 탈퇴·퇴출 시 모든 기존 회차 참여자의 `invalidatedAt`을 영구 설정한다. 재가입해도 userId 일치만으로 자격이 돌아오지 않는다.
- 탈퇴·퇴출·계정 영구 삭제는 N, 목표, 이미 기록된 기여와 성장량을 줄이지 않는다. 계정 삭제는 participant/reward/draw의 user FK를 NULL로 바꾸고 개인 달성 FK도 NULL로 익명화한다. 식별이 없는 참여자 UUID·기여 날짜·횟수는 그룹 원장에 남는다. 그룹장 계정 삭제는 기존 RESTRICT 정책대로 먼저 위임/탈퇴 또는 그룹 삭제가 필요하다.
- 그룹 삭제는 미션·기여·룰렛권·추첨·그룹 지급 명세를 CASCADE 삭제한다. 개인 완료 기록, 개인 해바라기씨와 `CurrencyTransaction`은 삭제하지 않는다. 계정 자체를 영구 삭제할 때의 기존 개인 데이터 삭제 정책은 별개다.

## 운동 성공 → 자동 물 주기

`WorkoutRoutinesService.event`와 `RecommendationsService.event`의 최초 유효 완료 전이에서 `recordActivityAchievement`를 호출한다. 조회/프로필, 시청 이벤트 수, 표시상 streak 값은 트리거가 아니다.

신규 루틴은 항목이 하나 이상이고 마지막 미완료 항목이 완료되어 **전체 루틴**이 성공할 때만 인정한다. 기존 일별 배정은 공통 활동 집계처럼 `assignmentDate != null`인 완료만 인정한다. `CurriculaService.complete`가 처리하는 날짜 없는 내부 배정은 제외한다. 기존 완료 판정, 서버 완료 시각, 클라이언트 시각 처리, v2의 KST 마감/만료 거절과 요청 재전송 계약은 유지한다.

1. 기존 사용자 행 잠금 아래 해당 KST 날짜의 달성 및 원본 완료 기록을 확인한다. 도입 전 당일 완료도 조회하므로 신규 경로로 다시 인정하지 않는다. 백필은 없다.
2. 사용자+KST 날짜 unique 달성 행을 저장한다. 당시 활성 회차가 없더라도 달성은 소비된 상태로 저장한다. 이후 시작 회차에 소급하지 않는다.
3. 소속 그룹 행을 UUID 순서로 잠근다. 회차 시작 시각이 서버 달성 시각보다 늦거나 참여자가 없거나 영구 무효화되었으면 해당 그룹을 건너뛴다. 다른 그룹의 자격에는 영향을 주지 않는다.
4. 그룹별 달성 unique 원장과 개인/회차 물 횟수를 함께 저장한다. 원본 완료·이벤트 저장과 **모든** 그룹 반영은 같은 트랜잭션이다. 어느 한 그룹에서 실패해도 전체 롤백된다. outbox나 새 인프라는 없다.
5. 동일 날짜의 다른 루틴/기존 배정/기기/요청 키는 다시 반영하지 않는다. 같은 날 새 회차를 시작해도 이미 반영된 달성을 재사용하지 않는다. 시작 전 완료, 과거 완료와 그 재전송도 소급하지 않는다.

물은 보관·수동 투입·재화 차감 없이 해당 회차에 자동 반영된다. 개인 스트릭이 끊겨도 누적 기여는 남는다.

| 단계     | 누적 물 주기 범위   | 응답 stage  |
| -------- | ------------------- | ----------- |
| 씨앗     | 0 이상, N 미만      | `seed`      |
| 새싹     | N 이상, 3N 미만     | `sprout`    |
| 줄기     | 3N 이상, 7N 미만    | `stem`      |
| 꽃봉오리 | 7N 이상, 14N 미만   | `bud`       |
| 해바라기 | 14N 도달, 회차 완료 | `sunflower` |

각 목표는 회차 시작부터의 누적값이다. 단계별 요구량을 더한 25N이 아니다. 마지막 물 주기도 개인 기여에 포함하고, 완료 회차에는 추가 기여를 저장하지 않는다.

## 룰렛권과 추첨

해바라기 완성 트랜잭션에서 자격을 유지한 참여자에게 `floor(개인 누적 기여 / 7)`장을 발급한다. 6/7/14/20/21회는 각각 0/1/2/2/3장이다. 연속 7일 조건이나 다음 회차로의 나머지 이월은 없다. 회차 완료·발급은 그룹 잠금 및 회차 상태 전이로 한 번만 실행하고, `(roundId, participantId, ordinal)`도 unique다.

권은 원래 그룹·회차·참여자에 연결된다. 다음 회차가 시작되어도 보관하고 그룹과 기존 멤버십이 유지되는 동안 만료되지 않는다. 탈퇴·퇴출하면 미사용 권도 영구 무효다. 재가입으로 복구되지 않는다. 이미 지급받은 개인 재화는 그룹 탈퇴·퇴출·삭제로 회수하지 않는다.

| 결과             | 확률 | 지급 대상/개수                       |
| ---------------- | ---- | ------------------------------------ |
| `self_1`         | 50%  | 추첨자 1개                           |
| `self_3`         | 25%  | 추첨자 3개                           |
| `self_5`         | 13%  | 추첨자 5개                           |
| `self_7`         | 7%   | 추첨자 7개                           |
| `contributors_3` | 4%   | 원래 회차의 유효 기여자 **각각** 3개 |
| `contributors_7` | 1%   | 원래 회차의 유효 기여자 **각각** 7개 |

단체 대상은 **해당 권의 원래 회차**에 1회 이상 기여했고 추첨 시점에도 당시 멤버십을 유지한 사용자다. 1–6회 기여자는 포함하고 기여 0회, 도중 신규, 탈퇴·퇴출·재가입자는 제외한다. 추첨자도 대상에 포함한다. 단체 결과에 별도 개인 보상을 더하거나 총액을 나누지 않는다.

정책 버전은 `sunflower-2026-09-30-v1`이다. 시작 때 버전과 전체 확률표를 회차에 고정 저장하고 DB가 변경을 막는다. 서버 `node:crypto.randomInt(100)`의 [0,100) 구간은 [0,50), [50,75), [75,88), [88,95), [95,99), [99,100)이다. 합계·구간·버전·금액·대상을 검증하며 새 정책 버전은 명시적 등록이 필요하다. 기존 권은 자신의 저장된 정책을 사용한다. 클라이언트가 결과/금액/수령자를 지정할 수 없다.

추첨 결과·수령자 명세·권 소비(권당 unique draw)·모든 재화 증가·개인 거래를 한 트랜잭션으로 커밋한다. `AvatarService.grantCurrencyInTransaction`은 기존 `grantCurrency`의 검증/중복 지급/잔액 상한/거래 기록 핵심을 재사용한다. 기존 3인자 호출 계약도 유지한다. 지급 키는 사용자별 `group-roulette:<drawId>`다. 한 명의 지급 실패·잔액 상한 초과도 전체 롤백한다. 저장된 결과의 재전송은 다시 추첨하거나 수령자를 다시 계산하지 않는다.

## API 계약

모든 경로는 `/api/v1/groups/:groupId` 아래다. 기존 Bearer 인증·CSRF/Origin·JSON strict 입력·UUID 소문자 정규화·Nest 오류·`Cache-Control: no-store`를 따른다. 신규 루틴의 기존 `/api/v2/workout-routines`와 단일 운동 `/api/v1/workouts`는 바꾸지 않는다.

| 메서드·하위 경로        | 입력                                                       | 권한/성공                                                  |
| ----------------------- | ---------------------------------------------------------- | ---------------------------------------------------------- |
| `POST /missions/start`  | JSON `{}`, UUID `Idempotency-Key` 필수                     | 현재 그룹장, 201 `{mission,replayed}`                      |
| `GET /missions/current` | 없음                                                       | 현재 구성원, 200 미시작 또는 최신 회차(활성 회차 우선)     |
| `GET /missions`         | `limit`, `cursor`                                          | 현재 구성원, 200 회차 페이지                               |
| `GET /roulette/tickets` | `limit`, `cursor`                                          | 현재 구성원, 본인 권만 200 페이지                          |
| `POST /roulette/spins`  | JSON `{ "ticketId": "UUID" }`, UUID `Idempotency-Key` 필수 | 현재 구성원+본인의 유효 권, 201 `{draw,replayed}`          |
| `GET /roulette/draws`   | `limit`, `cursor`                                          | 현재 구성원, 본인 추첨 또는 본인 단체 수령 이력 200 페이지 |

페이지는 기존 그룹과 같은 UUID 오름차순, 기본 limit 20/최대 50, `{items,nextCursor}`다. `nextCursor`는 UUID 또는 null이며 이력의 시간순을 뜻하지 않는다. 읽기는 상태 전이나 지급을 수행하지 않는다. 수동 물 주기·임의 운동 성공·중단·초기화 API는 없다.

미시작 응답은 `{ "status": "not_started", "id": null }`이다. 시작/현재/회차 이력의 회차 객체는 다음 형태다(식별자·수치는 설명용).

```json
{
  "id": "ed71ce6e-45d9-4971-8d1e-91e77b75461f",
  "groupId": "7fbd3a10-be7a-42e5-8f47-7a9656c17b01",
  "status": "in_progress",
  "startedAt": "2026-09-30T01:00:00.000Z",
  "completedAt": null,
  "memberCount": 2,
  "stage": "sprout",
  "waterCount": 3,
  "stageTargets": {
    "seed": 0,
    "sprout": 2,
    "stem": 6,
    "bud": 14,
    "sunflower": 28
  },
  "totalTarget": 28,
  "policyVersion": "sunflower-2026-09-30-v1",
  "me": { "eligible": true, "reason": "eligible", "waterCount": 2 }
}
```

`status`는 `in_progress`/`completed`다. `me.reason`은 `eligible`, `not_in_snapshot`(시작 후 가입), `membership_ended`(탈퇴 후 재가입)다. 이전 기여량은 자격이 끝난 후에도 표시한다. 자격은 완료 상태와 별개며 완료 회차에 물을 더 주지는 않는다.

권 객체: `{id,roundId,createdAt,policyVersion,status,usable,usedAt,invalidatedAt}`. status는 `available`/`used`/`invalidated`다. 이미 사용한 권은 used가 우선하고, 재가입자는 기존 미사용 권이 invalidated임을 확인할 수 있다. 다른 사용자의 권은 404다. 구성원 자격을 잃으면 그룹 조회 자체가 403이다.

추첨 객체: `{id,ticketId,roundId,drawnAt,policyVersion,result,amountPerRecipient,recipients,myReward}`. `recipients`는 저장된 `{userId,amount}` 목록이고 계정 영구 삭제는 userId null로 익명화된다. `myReward`는 본인의 `{amount,transactionId}` 배열이다. 다른 사용자의 잔액·보유 목록·구매 기록을 포함하지 않는다. 그룹 삭제 뒤에도 개인 재화 거래 자체는 남지만 그룹 추첨 API에는 접근할 수 없다.

같은 시작 키+같은 그룹은 기존 회차의 현재 상태를 반환한다. 같은 추첨 키+같은 권은 저장된 결과를 반환한다. 같은 키+다른 그룹/권은 409다. 요청 키는 작업 종류별 사용자 단위이며 그룹 삭제 시 기록도 삭제된다. 재시도 전에 **현재 권한과 기존 참여 자격**을 다시 검사한다. 위임 후 이전 그룹장의 시작 재시도나 탈퇴/재가입자의 기존 추첨 재시도는 권한을 복구하지 않는다.

주요 오류: 400 입력/필수 키/미지원 필드, 401 미인증, 403 구성원/그룹장/참여 자격/CSRF, 404 그룹/본인 권 없음, 409 최소 인원/활성 회차/키 충돌/사용한 권/잔액 한도. 재화 누락은 기존 `CURRENCY_MISSING` 503이다. ‘꽝 없음’은 유효 추첨의 결과 정책이며 요청 오류를 보상으로 바꾸지 않는다.

## 잠금·무결성·삭제

- 시작·가입 승인·탈퇴·퇴출·위임·삭제·기여·룰렛은 동일 그룹 행 `FOR UPDATE`를 사용한다. 원장/참여자를 멤버십의 CASCADE 하위에 두지 않는다. 멤버십 DELETE trigger가 직접 DB 삭제와 계정 CASCADE까지 영구 자격 무효화한다.
- 운동/그룹 생성·신청/상점 구매의 사용자 잠금은 `FOR NO KEY UPDATE`다. 사용자 간 직렬화와 계정 삭제 보호를 유지하면서, 그룹 스냅샷/룰렛의 `FOR KEY SHARE` 계정 보호와 호환된다.
- 여러 그룹은 UUID 순서, 여러 수령자와 재화는 user UUID 순서다. 계정 DELETE trigger도 관련 그룹을 UUID 순서로 잠근다. 계정 삭제의 사용자→그룹과 그룹 관리의 그룹→대상 사용자 사이 잔여 FK 교착은 PostgreSQL이 중단하며 전체 트랜잭션을 최대 4회 재시도한다. raw query의 adapter 내부 SQLSTATE `40P01`/`40001`와 Prisma `P2034`를 처리한다. 비밀번호 hash 조건을 포함한 계정 DELETE도 모든 CASCADE를 다시 실행한다.
- 시작/추첨의 동일 요청 키는 사용자·작업·키별 transaction advisory lock으로 그룹 간 재사용까지 직렬화한다. 사용자 전체/그룹 전체를 공통 전역 잠금으로 직렬화하지 않는다.
- 활성 회차 partial unique, 고정 N/14N/성장 범위 CHECK, 회차/참여자 불변 trigger, 그룹별 달성 unique, 회차별 권 ordinal unique, 권당 draw unique, 사용자별 지급 이벤트 unique, 지급 명세 사용자 unique를 둔다. 복합 FK는 원장과 권의 회차/참여자 혼합을 막는다. Prisma에서 표현하지 못하는 partial index·CHECK·trigger·추가 복합 FK는 SQL 마이그레이션을 보존한다.
- 개인 달성은 계정 소유, 미션 원장은 그룹 소유, 개인 재화 거래는 계정 소유다. 그룹 데이터에서 개인 완료/거래로 향하는 CASCADE는 없다.

## 배포·검증 경계

마이그레이션은 `prisma/migrations/20260930000400_group_missions/migration.sql`이다. 기존 행 수정·과거 성장 생성·재화 지급·개인 완료 백필은 없다. 현재 그룹과 데이터가 있는 상태의 신규 마이그레이션 적용 및 전용 DB 임시 스키마 전체 적용/재적용을 검증한다.
