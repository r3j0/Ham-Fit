# 그룹·가입 신청·알림 API

2026-09-29 사용자 요구사항에 따른 구현. 모든 경로는 `/api/v1` 아래이며 Bearer access token이 필요하다. 변경 요청은 기존 인증 규칙에 따라 `X-CSRF-Protection: 1`이 필요하고, 브라우저 Origin은 설정된 프론트엔드 Origin과 일치해야 한다. JSON 입력은 `Content-Type: application/json`으로 전송한다. 모든 응답에 `Cache-Control: no-store`를 적용한다.

공개/비공개 구분, 공개 검색, 공개 목록, 즉시 가입, 정원 수정 API는 없다. `GET /groups`는 인증된 사용자의 소속 그룹만 반환한다.

## 구현 범위

그룹 생성·조회·수정·삭제, 초대 코드 조회, 신청·승인·거절, 구성원 프로필, 퇴출·탈퇴·그룹장 위임, 저장형 알림 목록·읽음 처리를 제공한다. 초대 코드는 가입 신청용 토큰이며 암호학적 개인 키가 아니다. 그룹 기여·씨앗·성장 로직은 실행하지 않는다. [미션 연동 경계](group-missions.md)에 확인한 기존 완료 경로와 미정 정책을 정리했다.

## 입력 규칙

기존 Zod strict object·UUID 검증·입력 오류 형식을 따른다. 알려지지 않은 입력 필드는 400이다. 새 제한은 다음과 같다.

| 필드/기능         | 규칙                                                                                              |
| ----------------- | ------------------------------------------------------------------------------------------------- |
| `name`            | 필수 문자열, NFC 정규화·양끝 공백 제거 후 1–50 UTF-16 코드 단위                                   |
| `description`     | 필수 문자열, 같은 정규화 후 0–500 코드 단위. 빈 문자열로 소개 비우기 가능                         |
| 그룹 텍스트       | 제어 문자와 Unicode format 문자 금지. 줄바꿈도 금지                                               |
| `maxMembers`      | 그룹장 포함 1–100 정수. 생성 시만 설정. 운영상 응답·구성원 처리량 제한이며 미션 정책과 무관       |
| `inviteCode`      | 양끝 공백 제거 후 43자리 base64url. 대소문자 구분. 서버의 `randomBytes(32)`로 생성한 256비트 토큰 |
| `Idempotency-Key` | 생성·가입 신청에 필수 UUID. 작업 종류별 사용자 단위로 구분                                        |
| ID                | UUID, 소문자로 정규화                                                                             |
| `limit`           | 기본 20, 1–50. `cursor`는 직전 페이지 `nextCursor` UUID                                           |
| 가입 신청 호출    | 계정당 분당 10회. 기존 DB 기반 rate limit 재사용. 기존 변경 요청 IP 제한(분당 60회)도 적용        |

초대 코드는 구성원이 복사·공유할 수 있도록 DB에 복원 가능한 형태로 저장한다. 일반 조회·알림에는 포함하지 않으며 코드 로깅도 추가하지 않는다. 이번 범위에는 코드 만료·교체 정책이 없다. 운영 프록시/APM에서도 신청 본문을 수집하지 않도록 기존 민감 입력 로깅 원칙을 적용한다.

## API 목록

표의 경로에는 `/api/v1`을 붙인다. `G`, `U`, `R`, `N`은 각각 그룹·사용자·신청·알림 UUID다.

| 메서드·경로                              | 권한          | 요청                                                              | 성공                                  |
| ---------------------------------------- | ------------- | ----------------------------------------------------------------- | ------------------------------------- |
| `POST /groups`                           | 로그인 사용자 | 생성 JSON + 요청 키                                               | 201 그룹 요약·본인 역할               |
| `GET /groups`                            | 로그인 사용자 | `limit`, `cursor`                                                 | 200 본인 그룹 페이지                  |
| `GET /groups/G`                          | 해당 구성원   | 없음                                                              | 200 그룹 요약·그룹원 목록             |
| `GET /groups/G/members/U`                | 해당 구성원   | 없음                                                              | 200 해당 그룹원 프로필·역할·가입 시각 |
| `GET /groups/G/invite-code`              | 해당 구성원   | 없음                                                              | 200 `{ "inviteCode": "..." }`         |
| `PATCH /groups/G`                        | 해당 그룹장   | `name`, `description` 중 1개 이상                                 | 200 그룹 요약                         |
| `POST /groups/join-requests`             | 로그인 사용자 | `{ "inviteCode": "..." }` + 요청 키                               | 201 신청                              |
| `GET /groups/G/join-requests`            | 해당 그룹장   | `status`(기본 pending, approved/rejected 가능), `limit`, `cursor` | 200 신청 페이지·신청자 닉네임         |
| `POST /groups/G/join-requests/R/approve` | 해당 그룹장   | 본문 없음                                                         | 200 처리된 신청                       |
| `POST /groups/G/join-requests/R/reject`  | 해당 그룹장   | 본문 없음                                                         | 200 처리된 신청                       |
| `POST /groups/G/leadership`              | 해당 그룹장   | `{ "userId": "U" }`                                               | 204                                   |
| `DELETE /groups/G/members/U`             | 해당 그룹장   | 없음                                                              | 204. 그룹장 대상은 금지               |
| `DELETE /groups/G/members/me`            | 해당 구성원   | 없음                                                              | 204                                   |
| `DELETE /groups/G`                       | 해당 그룹장   | 없음                                                              | 204                                   |
| `GET /notifications`                     | 수신자 본인   | `limit`, `cursor`                                                 | 200 알림 페이지                       |
| `PATCH /notifications/N/read`            | 수신자 본인   | 없음                                                              | 200 알림. 기존 읽음 시각 유지         |
| `GET /users/me/profile/activity`         | 본인          | 없음                                                              | 200 그룹과 동일한 개인 활동 프로필    |

페이지는 UUID 오름차순으로 조회한다(시간순 피드 아님). 반환된 `nextCursor`를 그대로 사용한다. 응답 형식은 `{ "items": [...], "nextCursor": "UUID 또는 null" }`이며 실제 종료값은 문자열이 아닌 `null`이다. 신청은 상태 필터별로 페이지를 다시 시작한다. 페이지 사이 상태 변경·새 가입 등은 스냅샷으로 고정하지 않으며 갱신 시 첫 페이지부터 조회한다.

## 생성·조회 예시

```http
POST /api/v1/groups
Authorization: Bearer ACCESS_TOKEN
X-CSRF-Protection: 1
Content-Type: application/json
Idempotency-Key: 91004d71-b8c5-4c32-a56e-ed38349325af

{"name":"함께 운동","description":"매일 함께 운동해요","maxMembers":10}
```

```json
{
  "id": "6dd410b4-9113-4293-9bc7-5165583167a0",
  "name": "함께 운동",
  "description": "매일 함께 운동해요",
  "maxMembers": 10,
  "currentMembers": 1,
  "createdAt": "2026-09-29T08:00:00.000Z",
  "role": "leader"
}
```

그룹 상세는 위 요약에서 `role` 대신 `members` 배열을 제공한다. 수정 응답은 요약만 반환한다.

```json
{
  "id": "6dd410b4-9113-4293-9bc7-5165583167a0",
  "name": "함께 운동",
  "description": "매일 함께 운동해요",
  "maxMembers": 10,
  "currentMembers": 1,
  "createdAt": "2026-09-29T08:00:00.000Z",
  "members": [
    {
      "userId": "39fcd6bd-f0cf-4c3d-9ce2-4619d37060e2",
      "nickname": "운동친구",
      "profileCharacter": null,
      "streak": 2,
      "role": "leader",
      "joinedAt": "2026-09-29T08:00:00.000Z"
    }
  ]
}
```

예시 UUID·시간·스트릭은 설명용이다. 이메일·생년월일·계정 재화·비밀번호는 그룹 응답에서 조회하거나 직렬화하지 않는다. 미설정 닉네임은 기존 개인 프로필과 동일하게 `null`이다.

현재 프로필 캐릭터의 저장·선택·카탈로그 기능은 기존 BE에 없다. **`profileCharacter: null`은 미설정/소스 없음**을 뜻하며 임의 캐릭터나 보유 여부를 만들지 않는다. 캐릭터 선택 기능을 완성한 것으로 간주하지 않는다.

스트릭은 기존 FE `lib/workout-history.ts`의 개인 운동 이력 기준을 backend 공통 `member-profile.ts`로 구현했다. 데이터는 기존 `UserCurriculumAssignment`의 일별 배정(`assignmentDate != null`) 중 완료 상태와 `completedAt`이다. 완료 시각을 KST 날짜로 변환하여 같은 날짜를 한 번만 세고, 오늘 완료가 없으면 어제부터 연속 일수를 센다. 배정일 순서·최근 한 페이지로 절삭하지 않으며 미래 완료는 제외한다. 그룹별 계산 기준을 추가하지 않았다. `GET /users/me/profile/activity`와 그룹 조회가 같은 함수를 호출한다. 기존 `/users/me/profile` 응답은 유지한다. 새 루틴 항목의 완료를 개인 스트릭에 포함할지는 기존 개인 이력 계약이 바뀔 때 함께 변경해야 한다.

## 신청·처리·알림 예시

구성원이 초대 코드 API에서 복사한 실제 코드를 사용한다. 신청자는 아직 구성원이 아니므로 초대 코드 조회 API를 직접 사용할 수 없다.

```http
POST /api/v1/groups/join-requests
Authorization: Bearer APPLICANT_TOKEN
X-CSRF-Protection: 1
Content-Type: application/json
Idempotency-Key: 9aa4a4f9-fcae-49e2-a49b-2e7fdb56ca67

{"inviteCode":"COPY_THE_43_CHARACTER_CODE_FROM_A_MEMBER_HERE"}
```

```json
{
  "id": "c7c95cb3-f8fd-4b0b-8c0f-f49b71c21d85",
  "groupId": "6dd410b4-9113-4293-9bc7-5165583167a0",
  "userId": "499cbe67-f1de-464c-8f02-12e4a5af38bd",
  "status": "pending",
  "createdAt": "2026-09-29T08:01:00.000Z",
  "processedAt": null
}
```

그룹장이 `POST /groups/G/join-requests/R/approve`를 호출하면 동일 형식에서 `status: "approved"`, `processedAt: "처리 시각"`이 반환된다. 거절은 `rejected`다. 승인 전에는 구성원 수·접근 권한이 바뀌지 않는다. 정원이 가득 찼어도 신청은 가능하며 승인만 409가 된다. 다른 그룹의 가입·신청은 제한하지 않는다.

알림 목록 항목:

```json
{
  "id": "09ec209f-5449-4fc0-ab9f-7e8ebce32a56",
  "groupId": "6dd410b4-9113-4293-9bc7-5165583167a0",
  "requestId": "c7c95cb3-f8fd-4b0b-8c0f-f49b71c21d85",
  "type": "join_approved",
  "createdAt": "2026-09-29T08:02:00.000Z",
  "readAt": null
}
```

- 접수: 접수 트랜잭션에서 확인한 현재 그룹장에게 `join_requested`.
- 승인·거절: 신청자에게 `join_approved` 또는 `join_rejected`.
- 외부 push·메일·소켓 송신은 하지 않는다. 프론트엔드가 inbox API로 조회한다.
- 위임 전 접수 알림은 기존 수신자에게 남는다. 새 그룹장은 대기 신청 목록에서 모든 기존 신청을 처리할 수 있다. 위임 자체의 새 알림은 만들지 않는다.
- 탈퇴·퇴출 후 본인이 받은 결과 알림은 남지만 그룹 상세/신청 목록 접근 권한을 부여하지 않는다. 알림에는 그룹 내용·코드·신청자 개인정보를 복사하지 않는다. 그룹 삭제 시 관련 알림도 삭제한다.

## 재시도와 동시성

1. 생성은 사용자 행 잠금과 `(userId, key)` 제약으로 중복 생성하지 않는다. 정규화된 입력 hash가 다르면 409. 재시도 응답은 현재 그룹 요약이며, 생성자가 이후 탈퇴했다면 접근 권한을 다시 검사하여 403이다.
2. 신청은 사용자 행 및 그룹 행을 잠근다. 동일 키는 원래 신청의 현재 상태를 반환한다. 다른 키로 같은 그룹에 pending 신청이 있거나 이미 구성원이면 409다. 거절·퇴출·탈퇴 이후 **새 키**로 재신청한다. 기존 승인 신청 재시도는 재가입시키지 않는다. 같은 신청 키를 다른 그룹에 사용하면 409.
3. 승인·거절·위임·퇴출·탈퇴·삭제는 대상 `groups` 행을 `FOR UPDATE`로 잠근 뒤 DB에서 권한을 재확인한다. 승인 정원 확인, 멤버십 삽입, 신청 상태 변경, 결과 알림 저장이 한 트랜잭션이다. 승인·거절의 신청자와 위임 대상 계정에는 `FOR KEY SHARE` 잠금을 유지하여 계정 삭제 CASCADE와 경쟁하지 않게 한다. 대상 계정 삭제가 먼저 완료되면 404를 반환하며, 삭제된 사용자에게 멤버십·그룹장·알림을 생성하지 않는다.
4. 같은 신청에 같은 결정을 재전송하면 기존 결과만 반환한다. 반대 결정은 409. 처리 당시의 그룹장 권한을 다시 검사하므로 위임 후 이전 그룹장의 재시도는 403이다.
5. `(groupId, userId)` PK, pending 신청 partial unique index, 알림 `(requestId, type)` unique 제약을 둔다. DB capacity trigger도 그룹 행 잠금 후 정원을 검사하므로 내부 직접 INSERT도 정원 초과가 불가능하다. 멤버십 UPDATE는 금지하며, 생성/삭제로만 변경한다.
6. 그룹장 역할은 `groups.leader_user_id` 하나에서 계산한다. 필수 그룹장 ID + 해당 그룹 멤버십을 가리키는 **지연 검사 composite FK**로 커밋된 그룹에는 정확히 한 명의 현재 구성원 그룹장만 존재한다. 위임은 이 포인터 한 번의 변경이며 기존 그룹장은 일반 구성원이 된다.
7. 읽기는 구성원 인증과 데이터 조회를 동일 트랜잭션에서 수행한다. 상세·프로필·코드·신청 목록은 그룹 공유 잠금과 Repeatable Read로 사용자 계정 삭제를 포함한 일관된 스냅샷을 읽는다. 퇴출/탈퇴가 커밋된 후 시작한 요청은 즉시 차단한다. 먼저 시작되어 겹치는 조회는 자기 스냅샷을 완료할 수 있다.
8. PostgreSQL 교착/직렬화 충돌은 전체 트랜잭션을 최대 2회 재시도한다. 알림도 롤백된 뒤 함께 재실행된다. Redis·별도 큐·외부 인프라는 추가하지 않았다.
9. 위임·탈퇴·삭제의 성공 응답은 204. 위임을 다시 호출한 이전 그룹장은 403, 탈퇴 재시도는 403(그룹 삭제 시 404), 그룹 삭제 재시도는 404다. 퇴출 대상이 이미 없으면 204. 이 응답들은 새 알림/멤버십을 만들지 않는다.
10. 생성/신청 요청 키 보존 기간은 그룹 수명과 같다. 그룹 삭제 시 요청 키 기록도 삭제된다. 삭제된 그룹 생성의 과거 키를 재사용해 새 그룹 생성 요청을 보내는 것은 새 생성으로 취급한다.

## 탈퇴·삭제와 데이터 모델

기존 hard-delete 정책을 따른다. 일반 구성원은 바로 탈퇴/퇴출되며 그룹장 자신은 퇴출할 수 없다. 다른 구성원이 있으면 그룹장은 위임 후 탈퇴해야 한다. 그룹장 혼자 남은 상태에서 탈퇴하면 그룹 전체를 삭제한다. 그룹장은 구성원이 남아 있어도 명시적 그룹 삭제 API를 사용할 수 있다.

| 테이블                  | 역할·제약·삭제                                                                                             |
| ----------------------- | ---------------------------------------------------------------------------------------------------------- |
| `groups`                | 그룹 정보·정원·유일한 초대 코드·그룹장 ID. 그룹장 사용자 삭제 RESTRICT                                     |
| `group_memberships`     | 복합 PK, 사용자/그룹 FK. 그룹 또는 일반 구성원 계정 삭제 시 CASCADE                                        |
| `group_create_requests` | 사용자별 생성 키/hash/그룹 FK. 그룹/사용자 삭제 CASCADE                                                    |
| `group_join_requests`   | 신청 이력·상태·처리 시각. 사용자별 요청 키 unique, 그룹별 pending partial unique. 그룹/사용자 삭제 CASCADE |
| `group_notifications`   | 수신자·신청·그룹·종류·읽음 시각. 신청별 종류 unique. 그룹/신청/사용자 삭제 CASCADE                         |

마이그레이션: `prisma/migrations/20260929000400_groups/migration.sql`. 기존 행의 변경·백필 없이 새 테이블·함수·제약을 추가한다. Prisma가 표현하지 못하는 deferred FK·partial unique·capacity/immutable trigger는 SQL로 관리하며 삭제하지 않아야 한다. 기존 계정/개인 운동/다른 그룹에는 그룹으로부터의 cascade가 없다.

**계정 영구 탈퇴 보완:** 그룹장인 계정의 기존 `DELETE /users/me`는 DB FK로 차단되고 409를 반환한다. 먼저 위임 후 그룹 탈퇴 또는 그룹 삭제를 해야 한다. 일반 구성원 계정 삭제는 종전처럼 가능하며 멤버십·본인 신청·알림만 함께 삭제한다. 비밀번호 확인·원자 삭제·세션 폐기 계약은 유지한다.

그룹 미션·기여·성장 테이블은 아직 존재하지 않으며 이번에 임의 수치/단위로 만들지 않았다. 따라서 해당 데이터의 보존/삭제/정산은 **미구현**이다. 정책 확정 후 그룹 소유 FK(CASCADE), 기여자의 탈퇴와 분리된 원장, 완료/보상 이벤트 unique 키를 추가해야 한다. 이 배포를 미션 원장까지 완성한 것으로 간주하지 않는다.

## 오류 응답

기존 Nest 오류 형식을 사용한다. 입력 검증은 필드별 `errors` 배열을 추가하며 제출한 초대 코드를 반영하지 않는다.

```json
{
  "statusCode": 400,
  "message": "사용자 입력을 확인해 주세요.",
  "errors": [{ "field": "maxMembers", "message": "검증 오류" }]
}
```

```json
{
  "statusCode": 409,
  "message": "그룹 정원이 가득 찼습니다.",
  "error": "Conflict"
}
```

| HTTP | 대표 원인                                                                                                                      |
| ---- | ------------------------------------------------------------------------------------------------------------------------------ |
| 400  | 잘못된 UUID/코드 형식, 필수 키 누락, 길이/정원 범위, 미지원 필드·빈 수정                                                       |
| 401  | 미인증·만료·삭제 계정                                                                                                          |
| 403  | 해당 그룹 구성원 아님, 일반 구성원의 관리 기능, CSRF/Origin, 위임 후 이전 그룹장                                               |
| 404  | 삭제/없는 그룹·그룹원·신청, 존재하지 않는 정상 형식 코드, 타인 알림                                                            |
| 409  | 기존 구성원/대기 신청, 정원 초과, 다른 결정으로 재처리, 요청 키 재사용 충돌, 그룹장 탈퇴·자기 퇴출·자기 위임, 그룹장 계정 삭제 |
| 429  | 기존 IP/신청 계정 호출 제한                                                                                                    |

프론트엔드는 승인 409 시 대기 신청을 유지하고 정원/권한 상태를 다시 조회한다. 임의로 승인 성공 상태를 표시하지 않는다.

## 적용·검증

모든 명령은 `backend/`에서 실행한다.

```bash
npm run db:validate
npm run db:generate
npm run db:migrate:deploy
npm run build
npm run test:e2e -- test/groups.e2e-spec.ts
```

운영에서는 먼저 새 마이그레이션을 적용한 뒤 새 서버를 배포한다. 서버 시작 시 자동 적용하지 않는다. 이 작업에서는 테스트 전용 DB의 임시 스키마에만 적용하며 개발/운영 DB에는 배포하지 않았다. 검사 결과와 변경 파일은 [검증 기록](groups-verification.md)을 참고한다.
