# 당일 운동 루틴 메커니즘 재검토 — 2026-09-29

후속 구현: 당일 추천·하루 한 루틴·80% 완료 판정으로 수정했다. 최신 동작은 [루틴 v2 계약](routines-api.md)을 따른다. 아래는 수정 전 감사 기록이며, 스트릭·심폐 슬롯·기준 미달 입력은 이번 변경에 포함하지 않는다.

검토 기준: 로컬 HEAD `a29fa29`와 현재 작업 파일. 사용자 목표는 **앱을 이용하는 날의 루틴을 추천받고, 그 루틴의 영상을 보며 운동하고, 수행 기록을 다음 추천에 반영하는 것**이다. 사용자 추가 지시에 따라 프론트엔드는 이번 판정·개선 범위에서 제외했다. 백엔드·DB 정의·원본 Python/CSV·기존 검사 코드를 확인했다. 서비스 코드, 원본 데이터, 개발·운영 DB는 변경하지 않았다.

앞선 `data-analysis-audit-2026-09-29.md`의 “핵심 추천 계산·입출력 연결은 일치한다”는 원본 래퍼와 BE 사이의 정합성 판정이었다. **제품 목표인 당일 추천이 되는지를 확인한 판정이 아니었으며, 그 기준으로는 현재 연결이 잘못됐다.** `below-standard-and-generation-review.md`의 다음날 사전 생성 제안 역시 이번에 명확해진 제품 목표에 적용하지 않는다.

## 다음날 알고리즘의 존재와 계산 시점

현행 `data-analysis/src/recommendation_v2.py`에는 서로 날짜 의미가 다른 함수가 있다.

| 함수                                             | 날짜 의미                              | 의도된 사용 시점                                                |
| ------------------------------------------------ | -------------------------------------- | --------------------------------------------------------------- |
| `recommend_workout_routine(..., current_date=D)` | D일의 루틴                             | D일 루틴이 필요할 때                                            |
| `run_recommendation(..., current_date=D)`        | 내부에서 D+1을 위 함수에 전달          | D일 운동 기록까지 확보한 뒤 다음날 루틴을 계산할 때             |
| `calculate_weight_adjustment(logs, D)`           | D 기준 노출도와 D+1 기준 노출도의 차이 | 오늘 운동 기록을 포함해 다음 추천에서의 노출도 변화를 계산할 때 |

근거: 원본 305행, 853행, 922행, 963행. 이전 단일 영상 모듈 `recommendation.py:628`에도 다음날 기준 진입 함수가 있다. Git 이력상 이전 모듈 추가는 `92f3493`(2026-09-24 01:00:05 KST), v2 추가는 `1d6ed22`(2026-09-28 23:55:24 KST)다. 이는 파일 추가 이력이며 알고리즘 아이디어의 최초 작성 시각까지 뜻하지 않는다.

“측정 시기”는 아래 세 가지를 구분해야 한다.

- **체력 측정값:** BE가 추천 요청 때 저장된 측정 중 `measuredOn DESC, createdAt DESC, id ASC` 첫 한 건의 기존 평가를 읽는다. 매일 다시 체력을 측정하거나 운동 종료 시 등급을 올리는 구조가 아니다. Python에는 그 등급만 전달하며 측정일·측정 ID는 BE 스냅샷에 남는다. 원본은 측정 시점을 판단하거나 측정값의 유효기간을 검사하지 않는다.
- **운동 기록 반영:** 추천일 D 기준 노출도는 D−14부터 D−1까지의 기록만 사용한다. 완료는 1.0, 중단은 0.5 가중치이며 7일 반감기를 적용한다. D일 기록은 당일 노출도에는 포함되지 않고 D+1 추천에서 포함된다. 최근 영상 제외는 별도로 D 당일부터 D−7까지를 포함한다.
- **실제 실행 시점:** 원본은 호출 때만 계산하는 함수다. 자정 예약 실행이나 운동 완료 감지는 없다. 현재 BE도 `POST /workout-routines/next` 요청 때 실행하며, 오늘 운동이 끝났는지 검사하지 않는다. 운동 완료 이벤트는 기록을 저장할 뿐 추천을 실행하지 않는다.

예: 9월 29일 밤 운동 완료 로그를 전달해 `run_recommendation(..., '2026-09-29')`를 부르면 **그 요청 시점에** 9월 30일 루틴을 계산한다. 9월 30일까지 기다리거나 새 체력 측정을 하는 것은 아니다.

`weightAdjustment`는 체력 향상량이나 등급 상승량이 아니라 **운동 이력으로 계산한 노출도의 날짜 간 변화**다. 오늘 운동의 반영뿐 아니라 이전 기록의 감쇠·기간 이탈도 포함하므로 음수가 될 수 있다.

## 우선 수정이 필요한 문제

### 1. [P1] 당일 루틴을 만들고 즉시 시작할 경로가 없다

- `scripts/recommendation-runner.py:23`은 다음날용 `run_recommendation`만 호출한다.
- `src/recommendations/workout-routines.service.ts:93`은 배정일을 오늘+1로 저장한다.
- 같은 서비스 `current():212`는 오늘 배정만 반환하고, `event():273`은 미래 배정의 운동 시작을 `ROUTINE_NOT_DUE`로 거부한다.
- 오늘 배정이 없는 사용자가 오늘 생성 API를 호출해도 오늘 조회는 계속 null이며, 생성된 운동을 오늘 시작할 수 없다. 자정 후 새 요청도 다시 그 시점의 내일을 만든다.

**필요 변경:** 당일 생성 경로에서 원본 `recommend_workout_routine`을 오늘 날짜로 호출하고 오늘에 배정한다. 오늘 저장값이 있으면 같은 루틴과 진행을 돌려준다. 원본 계산식을 BE에 복제하거나 래퍼에 어제 날짜를 전달하는 우회는 피한다. 어제 날짜 우회는 weightAdjustment의 날짜 의미와 동일 입력에 대한 기록 처리까지 어긋나게 한다.

### 2. [P1] DB도 다음날 배정을 강제한다

`prisma/migrations/20260929000100_workout_routines/migration.sql:14`에 `CHECK (assignment_date = reference_date + 1)`이 있다. 서비스에서 두 날짜를 오늘로 바꾸기만 하면 이 제약에 걸린다. 루틴 행은 UPDATE도 막혀 있다.

**필요 변경:** 기존 마이그레이션을 덮어쓰지 않고 후속 마이그레이션에서 당일 기준을 지원해야 한다. 기존 미래 배정·진행·생성 요청 키를 어떻게 보존할지도 함께 다뤄야 한다. 기존 기록의 날짜를 무조건 당겨서는 안 된다. `nextWorkout` 응답 계약·필수 weightAdjustment·문서·테스트까지 함께 정리해야 한다.

### 3. [P1] 운동 전 확정한 내일 루틴에 실제 오늘 운동이 누락될 수 있다

`next()`에는 오늘 루틴 완료 전제조건이 없다. 아침에 내일 배정을 만들면 당시 로그로 결과가 확정된다. 저녁에 오늘 운동을 끝내도 완료 이벤트는 항목만 갱신하며, 같은 내일 배정 요청은 저장값을 재사용한다. 원본 주석의 “오늘 운동 수행 후”라는 가정을 BE가 보장하지 않는다.

**당일 흐름에서의 해결:** 내일 선생성을 일반 사용자 흐름에서 제거하고, 다음 날 이용할 때 그날 루틴을 계산한다. 오늘 루틴은 수행 중 바뀌지 않도록 유지하되 이후 완료 로그는 다음 날짜의 추천에 반영한다. 오늘 전체 완료는 다음 날 추천의 필수 조건이 아니다.

### 4. [P2] 수행했어도 종료·완료 이벤트가 없으면 추천 이력에서 빠진다

`playback.ts:112` 이후의 상태 전이에서 `progress`·`pause`는 `in_progress`를 유지한다. `workout-routines.service.ts:311`은 최종 상태일 때만 `resultStatus/performedAt`을 기록하고, `logs():361`은 interrupted/completed 결과만 읽는다.

재현 조건: start → 영상의 60% 구간 progress → pause → 이후 요청 없음. 저장 구간은 있지만 결과는 미확정이므로 다음 추천 로그에는 포함되지 않는다. 미확정 상태를 날짜 전환이나 장기 비활동으로 확정하는 BE 처리도 현재 없다. 명시적으로 end를 보내면 50% 기준으로 중단/미진행이 확정된다.

또한 로그 날짜는 클라이언트 `occurredAt`이 아니라 **서버가 최종 이벤트를 접수한 시각**이다. 23:59에 수행하고 00:01에 처음 접수되면 다음날 운동으로 기록된다. 같은 항목을 다른 날 이어서 완료하면 이전 중단 결과를 대체해 최종 결과 한 건만 추천에 전달한다. 중복 방지에는 맞지만 날짜별 수행량 이력은 아니다.

**필요 결정:** 비활동 항목을 언제 중단 확정할지, 지연 전송·자정 경계·여러 날 이어하기에서 어느 날짜의 활동으로 인정할지 명시해야 한다. 시청만으로 완료 처리하는 변경은 이 검토에서 제안하지 않는다.

### 5. [P2] 새 루틴 완료가 활동 프로필·그룹 스트릭에 반영되지 않는다

`src/users/member-profile.ts:37`은 기존 `userCurriculumAssignment`만 읽는다. 신규 루틴 항목을 전부 완료해도 해당 데이터는 읽지 않으므로, 신규 루틴만 수행한 사용자의 활동 프로필/그룹 스트릭이 늘지 않는다.

**필요 변경:** 당일 루틴 완료와 하루 활동 성공의 관계를 정하고 공통 활동 조회에 신규 루틴을 포함한다. 부분 수행과 전체 완료를 같은 개념으로 임의 처리하지 않는다.

## 추천 내용과 입력 의미의 문제

### 6. [P2] 심폐지구력 측정값이 실제 루틴 선택에 영향을 주지 못한다

원본 `recommendation_v2.py:123`의 슬롯에는 근력·근지구력, 민첩성·순발력, 유연성만 있다. 현재 CSV의 심폐지구력 비중이 0보다 큰 영상은 2개이며, 둘 다 어느 주운동 그룹에도 들어갈 수 없다. 정리운동 조건에도 들어가지 않는다. 따라서 현재 데이터에서는 심폐지구력이 가장 취약해도 그 요인을 위한 영상이 선택되지 않는다. 체형 관리 목적의 심폐 가중치 1.2도 선택에 영향을 주지 못한다.

실행 확인: 나이 13/25/64 × 목적 3종 × 운동량 3종의 27개 조합에서 다른 등급을 2로 고정하고 심폐 등급만 1/3/null로 바꿨다. 동일 난수 시드와 빈 로그·빈 도구 목록에서 모든 루틴 반환값이 동일했다.

이는 코드 주석에도 적힌 데이터·슬롯 제한이다. 6축 체력 상태를 루틴에 반영한다는 제품 목표와의 간극으로 다뤄야 하며 BE가 임의의 다른 영상으로 대체해서는 안 된다.

### 7. [P2] 기준 미달과 미측정이 추천 단계에서 같은 값이 된다

`routine-algorithm.ts:51`은 graded 상태 외에는 null을 전달한다. below_standard, unevaluable, not_measured가 모두 원본의 미측정 처리로 합쳐진다. 실제 원본 실행에서 목적 grade·노출도 0인 축의 우선순위는 숫자 3이면 2.0, null이면 1.5다. 즉 유효하게 측정됐으나 기준 미달인 축의 의미를 추천기가 받지 못한다.

**필요 변경:** 입력에 상태를 전달하는 계약을 데이터 팀과 맞춘다. 임의의 공식 4등급을 만들어 전달하는 해결책은 부적절하다. 이번 검토는 공식 등급표를 다시 판정한 작업이 아니라 현재 상태 변환과 계산 결과를 검증한 것이다.

### 추가로 명확히 해야 할 기존 정책

- 측정은 최신 **한 기록**만 선택한다. 새 부분 측정을 저장하면 이전 기록의 다른 축 등급은 자동 병합되지 않는다. 미측정으로 남는 것이 현재 계약이며, 최신 축별 측정의 통합 프로필을 사용하는 추천은 아니다.
- 원본은 측정값 없이도 계산할 수 있지만 BE는 측정 기록·생년월일·운동 목적을 요구한다. 기존 온보딩 정책이며 날짜 오류와 구분해야 한다.
- 기존 날짜의 루틴·진행은 새 측정이나 설정 변경에도 고정된다. 운동 시작 전 변경과 이미 진행한 뒤의 변경을 다르게 취급할지는 별도 정책이다.
- `exclude_recent_videos`의 조건은 0 ≤ 경과일 ≤ 7로 오늘을 포함해 **8개 달력 날짜**다. “최근 7일”이라는 표현과 경계가 다르므로 문서와 의도를 맞춰야 한다. 구성 불가 시에는 원본이 이 제외를 풀고 다시 구성한다.
- 영상 재생 길이와 운동 처방량은 다르다. 현재 BE 완료는 명시적 complete 이벤트에 의한 자기 확인이며, 반복 횟수·세트 수를 별도로 증명하거나 집계하지 않는다. `estimatedMinutes`도 항목당 2분 추정치다. 이 자체를 자동 완료 오류로 판정하지는 않았다.

## 당일 추천을 위한 기준 흐름

1. 서버 KST 오늘 D를 정하고 D의 저장된 루틴이 있는지 확인한다.
2. 있으면 동일한 항목·처방·진행을 반환한다. 없으면 저장된 측정·설정·도구와 확정된 운동 기록을 읽는다.
3. 원본 `recommend_workout_routine(..., current_date=D)`로 계산하고 D에 배정한다. 노출도는 D−1까지의 과거 기록을 사용한다.
4. 항목별 start/progress/pause/end/complete와 진행을 저장한다. 전체 완료는 모든 항목 완료로 판정한다.
5. 다음날 D+1에 이용하면 그 시점에 새 당일 루틴을 계산한다. 어제 D의 확정 기록이 자동으로 노출도 계산 범위에 들어간다.

이 흐름에는 내일 루틴 선생성이나 자정 전체 사용자 일괄 생성이 필수적이지 않다. `weightAdjustment`를 유지한다면 “어느 날에서 어느 날로의 노출도 변화인가”를 별도 계약으로 명시하고, 오늘 루틴 생성·실제 운동 완료와 혼동하지 않아야 한다.
