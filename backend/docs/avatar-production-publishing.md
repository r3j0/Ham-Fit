# 프론트엔드 의상 배포와 상품 등록

2026-10-02 사용자 최종 결정으로 PNG·크기·위치·회전은 서비스 프론트엔드가 소유한다. 백엔드는 상품 ID·가격 및 기존 구매·착용 관계만 저장한다. Supabase DB는 유지하지만 의상용 Storage·Blob·PNG API는 사용하지 않는다.

## 전환 순서

1. 최신 frontend와 로컬 avatar-manager 코드를 같은 저장소에서 준비한다. 원본·수정 의상과 로컬 초안을 보존한다.
2. 편집기 `.env.local`에 `AVATAR_BACKEND_URL`, `AVATAR_MANAGER_TOKEN`, `AVATAR_FRONTEND_URL`을 설정한다. frontend가 다른 폴더에 있으면 `AVATAR_FRONTEND_DIR`을 지정한다.
3. 저장된 의상을 **프론트엔드 이미지·배치 내보내기**로 `frontend/public/hamsters/wardrobe`에 내보낸다. 업로드 API를 호출하지 않는다.
4. 정적 PNG·catalog·source-catalog·deployment·bundle 파일과 새 프론트엔드 코드를 함께 배포한다. 기존 DB의 이미지 API 경로도 해시를 보존해 프론트엔드 정적 경로로 해석할 수 있지만 최신 화면은 DB 표시 catalog를 읽지 않는다. 기존 운영 의상의 모든 원본·수정본을 정적 파일에 포함해야 한다.
5. 새 backend를 배포한다. `AVATAR_MANAGER_TOKEN`과 기존 DB·TLS 설정만 필요하며 의상용 Storage 비밀키는 필요 없다. DB 마이그레이션은 추가하지 않는다.
6. 편집기에서 상품을 조회하고 가격·판매 상태를 설정한 뒤 **상품 ID·가격 DB 등록**을 누른다. frontend 배포 확인 파일 하나를 검사하고 상품 정보만 한 번 POST한다. 등록 성공 시 구형 DB 표시 JSON을 비우고 기존 소유·구매·코디를 보존한다.

프론트엔드를 먼저 배포한 후 백엔드를 전환한다. 이전 편집기는 410으로 차단되므로 새 편집기로 바꾼다. 운영 전환 전 로컬 초안과 저장소 백업을 유지한다. Storage에만 존재하는 수정 PNG는 기존 백업에서 복구해 내보내야 하며 원본으로 조용히 대체하지 않는다. 자동 원격 이미지 내려받기나 운영 데이터 변경은 수행하지 않는다.

과거 Blob/Supabase 파일과 비밀키는 사용하지 않지만 이 변경에서 자동 삭제하지 않는다. 새 프론트엔드 표시를 확인한 뒤 별도로 정리한다. 다른 기능이 쓰는 Supabase 자격 증명이나 DB 설정을 삭제하지 않는다.

## 일상 작업

- 이미지·크기·위치·회전 변경: 로컬 저장 → 프론트엔드 내보내기 → 프론트엔드 배포. DB 등록은 필요 없다.
- 가격·판매 상태 변경: 상품 조회 → 수정 → DB 등록. 이미지 전송과 프론트엔드 재배포는 없다.
- 새 상품·새 지원 자세·착용 조합: 내보내기·프론트엔드 배포 → 검수 → DB 등록.
- 다른 PC: 최신 전체 저장소와 프론트엔드 정적 파일을 준비하고 **프론트엔드 편집본 불러오기**로 원본·수정본과 좌표를 로컬 복원한다.

서비스의 표시 catalog는 화면을 열 때 정적 파일에서 읽으며 API로 매분 폴링하지 않는다. 가격·보유·구매는 기존 상점 API를 사용한다. CDN 요청·전송과 배포 사용량은 호스팅 요금 정책에 따라 발생할 수 있지만 PNG당 API 함수 실행·Storage 읽기·등록 시 전체 PNG 업로드는 제거한다.

## 로컬 검증

편집기 `npm run check`, frontend `npm run check`, backend 단위 검사와 `npm run test:e2e -- test/avatar-assets.e2e-spec.ts`. 이미지 HTTP 전송 없음, 미배포 상태에서 DB 등록 차단, 가격 등록·수정 후 구매·보유·착용 유지, 표시 정보 입력 거절을 검사한다. 운영 업로드나 Storage 테스트는 실행하지 않는다.
