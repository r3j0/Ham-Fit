# 최신 백엔드 프론트 연동

기준: 백엔드 PR #9, `62b3f146a6c0a18be2eabded363685a23791edb8` (2026-09-30). 프론트엔드 `68c2b1e`에서 이어서 호환 작업을 적용했다.
기존 프론트 화면·인증·계정별 저장 복구 구조를 유지한다. 백엔드와 data-analysis는 변경하지 않는다.

개인 재화·마이룸·상점의 후속 작업은 아래 [구현 계획](#개인-재화마이룸상점-구현-계획-2026-10-01)을 따른다. 이 계획의 기능은 아직 구현 완료 항목이 아니다.

## 보유 운동 도구

`/account/preferences`에 6종(밴드·덤벨/아령·짐볼·줄넘기·스텝박스·볼) 복수 선택과 없음(빈 배열)을 제공한다. 기존 운동량·목적과 함께 `GET/PATCH /users/me/preferences`에 연결하고, 변경한 필드만 전송한다. 저장 결과가 불명확하면 원래 PATCH를 유지하고 재시도하며, 계정·화면 변경 후 늦은 응답은 폐기한다. 설정 변경은 다음 신규 루틴 생성부터 적용된다.

백엔드 브랜치의 도구 UI·어댑터·검사를 기존 프론트에 적용했다. API에 ownedTools가 없으면 조회 오류를 표시하므로 DB 마이그레이션과 최신 API 배포가 먼저다.

검증: 린트·타입·단위 126개·프로덕션 빌드 통과. Chromium 관련 11개 통과(실제 최신 API 2개, 오류·복구·반응형 계약 9개). 실제 PostgreSQL은 이번 검증의 별도 임시 디렉터리/포트에만 생성했다. 새로고침·재로그인·별도 브라우저 복원, 전체 선택/해제, 사용자 격리와 기존 계정 정보 보존을 확인했다.

## 검증 환경

기존 개발 서버와 캐시 충돌을 피하기 위해 `NEXT_BUILD_DIR=.next-integration`을 지원한다. 기본 실행 경로는 기존 `.next`다. 검증 서버는 `NEXT_PUBLIC_API_BASE_URL=http://localhost:3101/api/v1`로 빌드하고 3100 포트에서 실행했다. 테스트의 `E2E_BASE_URL`과 `E2E_API_BASE_URL`은 각각 이 프론트와 API 주소를 사용한다. 실제 배포 환경과 DB는 변경하지 않았다.

## 여러 운동으로 구성된 루틴

루틴 요청만 `/api/v2/workout-routines`의 `/current`, `/today`, `/history`, `/:id`, `/:id/items/:itemId/events`로 보낸다. 인증·측정·계정·그룹·기존 단일 운동은 v1을 유지한다. `/today`는 한국 시간 오늘의 루틴을 하루 한 번 생성하며 자동 생성하지 않는다. 응답 유실 후 새로고침에서도 동일 요청 키를 재사용하고, 이전 `routine:next`의 미확정 요청도 원래 키로 확인한다. 미래/과거 배정의 날짜와 처방을 오늘로 바꾸지 않는다.

오늘의 모든 처방·순서·세트·휴식·완료 수를 표시한다. nullable `cardioRecommendation`은 영상 목록 뒤에 걷기/뛰기와 분을 안내하며 가짜 영상·타이머·완료 이벤트를 생성하지 않는다. null 또는 필드가 누락된 이전 응답은 안내를 생략한다. `estimatedMinutes`는 `영상 운동 예상 …분 (유산소 제외)`로 구분한다. 항목별 실제 시청 구간이 80% 이상일 때 서버가 완료로 판정하고, 전체 영상 완료 여부도 서버 값을 따른다. `pause` 이후 미완료 항목은 `start`로 재개한다. 완료/종료 확인창을 여는 pause가 먼저 중단 상태를 확정하지 않도록 미디어 이벤트를 처리한다.

응답의 `serverTime`, `recordingAllowed`, `recordingExpiresAt`을 검증하고 요청 왕복 지연을 제외한 `performance.now()` 마감 시각을 사용한다. 시스템 날짜 변경·백그라운드 타이머 지연과 무관하게 공통 record 진입과 전송 직전에 검사한다. 자정이 지나거나 409 `ROUTINE_EXPIRED`를 받으면 큐·재시도를 종료하고 미확정 상태는 GET으로 확인한다. 같은 항목 revision에서도 서버 날짜 정보는 갱신한다. 재생 중인 영상 요소·재생 위치를 초기화하거나 멈추지 않는다. 과거 루틴은 다섯 상태 모두 기록 없는 영상 시청을 제공하고 과거 시청을 같은 영상의 오늘 항목에 저장하지 않는다.

기존 단일 운동 기록도 유지하고, 최신 백엔드의 `RECOMMENDATION_NOT_CONNECTED`는 이전 기록 조회 제한으로 명시한다. 운동 이력의 두 API 커서는 별도로 보관하여 더 보기 실패 시 이미 읽은 기록을 보존한다. 생년월일·측정·목적 준비 조건에는 해당 설정 화면 링크를 제공한다.

검증: 단위 129개 통과. 실제 Python 엔진의 루틴 생성·저장 복원·동일 날짜 재사용(201/200)·예약일 전 이벤트 거절을 검증했다. 브라우저 계약 검사에서 개별 운동 완료·완료 영상 재시청·응답 유실 복구·페이지 실패 복구를 확인했다. 기존 플레이어의 인증·복구·측정 타이머 구조는 유지한다. 외부 영상 제공 여부는 서버의 검증된 미디어 상태를 따른다.

## 그룹

하단 메뉴의 내 그룹 아이콘에서 `/groups`로 진입한다. 내 그룹 전체 조회, 이름·소개·정원을 통한 생성, 초대 코드 보기/복사, 가입 신청, 그룹장 승인·거절과 상태별 신청 목록, 멤버 프로필, 정보 수정, 강퇴·위임·탈퇴·삭제를 지원한다. 생성·가입 신청은 계정별 요청 저장소로 응답 유실 후 동일 키와 본문을 복원한다. 읽기 페이지의 잘못된 응답을 빈 목록으로 바꾸지 않으며, 화면 복귀 시 권한과 멤버 상태를 다시 읽는다. 그룹장 계정 탈퇴 409는 이메일 충돌로 표시하지 않고 그룹 관리로 안내한다. 생성과 초대 가입 폼은 두 열로 배치하고, 관리 버튼과 신청 상태 선택도 두 칸씩 배치한다.

검증: 실제 API 두 계정으로 생성 → 수정 → 초대 → 거절 → 재신청 → 승인 → 멤버 조회 → 무권한 수정 거절 → 그룹장 계정 탈퇴 차단 → 강퇴 → 재가입 → 위임 → 탈퇴 → 삭제 전 과정을 통과했다. 응답 유실·새로고침 복원, 다른 기기의 권한 변경, 잘못된 응답 거절을 별도 Chromium 계약 검사로 확인했다. 320/390/1280px 가로 넘침 검사와 화면 검토를 수행했다.

그룹 정보 수정은 편집 시작 시점과 비교하여 변경한 필드만 PATCH한다. 소개를 편집하는 동안 다른 기기가 바꾼 이름을 보존하는 실제 동시 수정 시나리오도 검증했다. 권한을 잃으면 그룹원 관리 대화상자와 설정의 편집·삭제 기능을 숨긴다. 일반 그룹원도 설정에서 탈퇴할 수 있다.

## 알림

메인 우측 상단 종 아이콘에서 `/account/notifications`로 진입한다. 가입 신청 도착·승인·거절을 구분하고, 서버에 읽음 상태를 저장하며 관련 그룹으로 연결한다. 전체 페이지를 중복 없이 병합하고 최신 생성 순으로 표시한다. 카드 여백과 글자 크기를 줄이고 링크와 읽음 버튼을 두 열로 배치한다. 읽음 저장에 성공하면 즉시 목록에서 제거하며, 새로고침 이후에도 서버의 읽음 상태를 기준으로 제외한다. 읽음 저장 실패 시에는 알림을 유지한다. 서버에는 기존 읽음 API를 사용하며 알림 데이터를 영구 삭제하는 API는 없다. 화면 복귀/명시적 새로고침/화면이 보이는 동안 60초 간격으로 최신 상태를 확인한다. 서버에 없는 푸시 발송이나 초대 코드 자동 회전 기능은 추가하지 않는다.

검증: 실제 두 계정의 신청·거절·승인 알림, 읽음 상태 저장, 타인 알림 읽기 404를 확인했다. 페이지 병합, 읽음 실패 후 재시도, 잘못된 응답, 320px 표시도 검증했다.

## 활동 통계

홈과 프로필은 `GET /api/v1/users/me/profile/activity`의 실제 `streak`를 사용한다. 프로필과 그룹원 상세는 서버가 제공하는 `longestStreak`, `totalWorkoutDays`도 표시한다. 서버는 모든 영상 항목을 완료한 루틴과 기존 완료 이력을 날짜별로 합쳐 집계한다. 레벨·컬렉션과 그룹원의 오늘 완료 여부는 아직 응답에 없으므로 실제 값으로 꾸미지 않는다. 조회 실패·다른 사용자 응답은 0이나 이전 성공값으로 표시하지 않는다.

`profileCharacter`의 저장 코디를 검증해 홈 그룹 슬라이드·그룹원 행·그룹원 상세에 반영한다. 기존 출력기를 재사용하며 현재 서버 카탈로그의 cream/gray × 13자세와 빈 의상 조합만 수용한다. 과거 응답의 null은 기본 크림으로 표시한다. 알 수 없는 ID·자세·의상·불일치 렌더링은 응답 오류로 처리한다. 그룹 슬라이드의 본인 제외·닉네임·그룹명·전환과 기존 반응형 구조를 유지한다. 상점 구매·코디 편집 화면은 이번 호환 변경 범위에 포함하지 않는다.

검증: 서버 값과 화면 복귀 갱신, 조회 실패/재시도, 응답 사용자 검증을 확인했다. 프로필 외형·활동·그룹·알림·달력 관련 Chromium 21개 통과, 320/390/430/1280px 기존 배치와 계정 메뉴를 검증했다.

## 실제 재생 통합 검사

`tests/e2e/workouts.spec.ts`는 실제 v2 `/today`로 추천을 생성하며 DB에 오늘 배정을 복사하는 fixture가 더 이상 필요하지 않다. 영상 전달/검증 메타데이터만 12초 MP4로 대체한다. 실제 시청 구간·탐색 제외·80% 미만 완료 요청·중단 후 start·복구 키와 저장 상태를 실제 API로 확인한다. 80% 경계와 다른 기기의 완료는 명시적인 이벤트 구간을 보내 API 계약을 검사하며, 이를 실제 외부 영상 시청 성공이라고 표시하지 않는다. 테스트 계정은 종료 시 삭제한다. 운영 데이터는 변경하지 않는다.

추가 회귀 검토에서 실제 UUID 정렬로 처방 순서가 바뀔 수 있는 부분을 수정했다. 같은 루틴 안에서는 서버 `order`를 우선하며, UUID가 역순인 단위 검사로 이를 고정했다.

공용 테스트 IP의 서버 요청 제한은 유지한다. 계정 생성·정리 중 명시적인 429가 오면 `live-api-fixtures.ts`에서 서버가 지정한 대기 후 재시도한다. 응답 유실이나 다른 실패를 이 준비 로직에서 자동 재전송하지 않는다. 기존 파일의 CRLF/LF를 보존하도록 Prettier `endOfLine: auto`를 명시했다.

## 브라우저 피드백 반영

홈의 그룹·알림 본문 링크와 프로필의 해당 메뉴를 제거했다. 알림은 메인 우측 상단 종 아이콘으로, 그룹은 하단의 독립 아이콘으로 이동했다. 하단 메뉴는 운동·메인·내 그룹·내 프로필 순서이며 그룹 하위 화면에서도 내 그룹을 활성 표시한다. 홈·프로필의 지정된 연속 운동 안내 문구를 삭제했다.

알림은 작은 카드와 두 열의 버튼을 사용한다. 읽음 상태를 서버에 저장한 뒤 목록에서 즉시 제거하고, 이미 읽은 알림은 전체 페이지를 불러온 후에도 제외한다. 읽음 저장 실패 시 알림을 유지하고 재시도할 수 있다. 그룹 생성·초대 가입 폼과 그룹 관리 선택 버튼은 두 열을 유지한다.

5. **대표 프로필 전파:** 본인 홈·내 프로필의 현재 고정 크림 캐릭터를 저장 코디에 연결하고 전신 코디가 보이도록 표시를 조정한다. 그룹 캐러셀·그룹원 목록·상세도 같은 출력기를 사용한다. 저장 응답 이후 본인 코디·개인 활동·그룹 조회를 무효화하고 다른 탭/기기의 화면 복귀 때 다시 읽는다. basic 미착용 호흡은 기존 렌더러를 재사용하며 다른 자세·의상을 임의 모션으로 변형하지 않는다.

7. **계정·통신 상태:** Bearer·CSRF·401 갱신·429 대기를 기존 `api`로 처리한다. 계정 전환·로그아웃·언마운트 뒤의 늦은 응답을 폐기하고 잔액·보유·코디·구매 미확정 요청을 사용자별로 격리한다. 조회 오류나 알 수 없는 의상을 기본 코디·성공 결과로 대체하지 않는다.

| PUT `/users/me/avatar/outfit`                     | `{ characterId, poseId, clothingIds }` 전체와 조회 당시 `If-Match` 전송   |
| GET `/users/me/profile/activity` 및 기존 그룹 API | 저장된 `profileCharacter`·서버 스트릭 재조회                              |

구매는 사용자별로 한 건씩 확정한다. 더블 클릭과 네트워크 오류·5xx·응답 유실에는 원래 UUID·body를 보존한다. 새로고침 후에도 미확정 구매를 복구할 수 있게 계정별 sessionStorage journal을 추가하며, 보유·잔액 자체의 진실은 서버에 둔다. 성공 응답의 inventory/currency로 갱신한 뒤 재조회한다. 이미 보유한 상품 409도 최신 inventory로 확인한다.

`CATALOG_CHANGED`는 최신 상품을 읽고 새 가격 확인 후 새 키로 요청한다. `INSUFFICIENT_FUNDS`는 최신 잔액을 읽고 부족 안내를 표시한다. 코드와 상태를 함께 구분하여 모든 409를 같은 오류로 표시하지 않는다.

코디 저장의 412는 편집 초안을 보존하고 최신 코디와 비교한 뒤 사용자가 다시 저장하도록 한다. 오래된 편집에 최신 ETag를 자동으로 붙이지 않는다. 저장 응답 유실은 GET으로 실제 코디와 revision을 확인한다. 403 미보유·422 미지원 조합은 inventory/catalog를 갱신하고, 503 누락 데이터는 조회 오류로 표시한다.

`lib/avatar-outfit.ts`의 현재 빈 `clothingIds/rendering.clothing` 전용 파서와 `ProfileCharacter`를 확장한다. 서버 상품 ID, `renderKey`, 에셋 ID, 슬롯을 구분하고 `clothingIds`와 렌더링 항목의 일치·슬롯 중복·에셋 지원을 검사한다. 완전한 조합은 BE `combinations`와 정확히 일치해야 하며 개별 의상의 지원 자세만으로 동시 착용을 추정하지 않는다.

### 부위별 에셋과 BE 상품 등록

현재 FE 스포츠웨어 4종은 합본 PNG다. 상·하의 분리와 자세별 손/팔 가림·클리핑·좌표 검증은 FE 작업이다. 기존 합본을 임의로 세트 상품으로 팔거나 색상만 바꿔 새 의상으로 등록하지 않는다.

기존 미추적 `deliverables/`를 읽기 전용으로 조사했다. `hamster-wardrobe-registered-data-v2-2026-09-29.zip`에는 아래 3개 아이템과 참조 PNG **80개**가 있으며 파일 누락은 없다. 이 자료는 재사용 후보이며 실제 화면 합성 품질·상품 등록은 아직 검증하지 않았다. 기존 스포츠웨어 4종의 분리를 대체한다는 결정도 하지 않았다.

동봉 studio에는 IndexedDB를 사용하지 않는 `createPortableWardrobe`, 800×1000 좌표계와 자세/캐릭터별 transform·레이어 이미지 경로가 있다. 해당 계약을 참고해 React 선언형 어댑터를 만들고 기존 FE의 보정된 viewBox와 실제 정렬을 확인한다. 편집기·IndexedDB·상품 가격을 운영 상태 저장소로 이식하지 않는다.

자료 자세는 14종으로 `phone/toilet/weight`가 BE 카탈로그에 없고 `a-plus/situp`은 자료에 없다. 현재 FE의 phone은 화면용 자세이고 사용자 소유 상품이 아니다. 기존 BE 13자세와 ID를 유지하며 새로운 자세를 넣거나 기존 자세를 제거하는 변경은 별도 상품/에셋 등록으로 진행한다.

BE 전달 규격은 안정적인 `clothing.<slug>` 상품 ID, `kind=clothing`, `slot/occupiesSlots`, 실제 `renderKey`, 에셋 버전·해시, `ownershipScope=shared`, 가격, **캐릭터+자세+전체 clothingIds** 조합과 시각 검증 근거다. 자료의 `item-*`는 에셋 ID로 매핑하며 바로 상품 ID로 쓰지 않는다. 실제 SKU 이름은 등록 전에 FE/BE가 맞춘다.

BE는 새 forward-only 마이그레이션으로 실상품·검증된 전체 조합을 등록한다. 판매 상태는 held에서 시작해 렌더러·에셋 배포와 검증을 마친 뒤 on_sale로 전환한다. 미지원 자세에서 옷을 조용히 제거하지 않으며 선택 제한 또는 명시적 해제 확인을 제공한다. 개별 아이템별 조합뿐 아니라 모자+상의+하의 및 서로 다른 의상의 혼합도 검증한다.

### BE 보상 후속 구현안

**하루 완료 보상:** KST 당일 루틴의 모든 영상 항목이 BE에서 completed로 확정되는 최초 시점에 날짜당 해바라기씨 1개를 지급한다. 안정적인 사용자+KST 날짜 지급 키로 재전송·다른 요청 키·동시 기기의 중복 지급을 막는다. 기존 스트릭·마감 정책을 그대로 사용하고 과거 기록에 소급 지급하지 않는다.

최신 `f577481`에 `AvatarService.grantCurrencyInTransaction(tx,userId,eventKey,amount)`이 추가되어 지급 핵심을 기존 TransactionClient에서 재사용할 수 있다. 개인 보상은 이 helper와 완료 처리의 날짜별 달성 경로를 검토해 **완료 저장·잔액 증가·거래 기록·개인 룰렛 자격 생성까지 같은 트랜잭션**으로 연결한다. 현재 날짜별 달성은 그룹 기여만 처리하고 직접 재화 1개를 지급하지 않는다. helper 분리 자체를 다시 구현할 필요는 없다. 독립 트랜잭션의 `grantCurrency()`를 완료 트랜잭션에서 호출하거나 완료 후 메모리 콜백으로만 지급하지 않는다.

**5일 배수 룰렛:** 전체 루틴 완료로 새 개인 운동일이 생겼을 때 서버가 스트릭을 집계하고 5·10·15일에 미사용 보상 티켓을 영구 생성한다. 예시 자격 키는 사용자+스트릭 시작일+milestone이며, 스트릭이 끊긴 뒤 새 5일 달성도 별도 자격으로 구분한다. 단순 조회나 FE의 `streak % 5`로 티켓을 발급하지 않는다. 기존 지급 완료 기록·과거 스트릭 소급 정책은 아래 확인 항목으로 둔다.

신규 API 제안은 `GET /users/me/rewards`(미사용 티켓·처리된 결과·다음 목표)와 `POST /users/me/rewards/roulette/:ticketId/draw`(Idempotency-Key, 서버 추첨·지급·사용 처리)다. **현재 제공되는 API가 아니며 BE와 확정할 계약이다.** 서버는 티켓 소유·미사용 상태를 검사하고 결과·지급·티켓 소비를 원자적으로 저장한다. 재요청과 새로고침은 저장 결과를 반환하고 다시 추첨하지 않는다. FE가 확률·금액·상품 ID·스트릭을 지급 요청으로 지정하지 않는다.

랜덤 코스튬·자세 지급에는 구매 외의 소유권 획득 경로가 필요하다. 현재 DB의 `AvatarOwnership.source`는 default/purchase만 허용하므로 reward 경로와 보상 기록을 새 마이그레이션으로 확장한다. 재화 결과는 기존 UserCurrency/CurrencyTransaction을 재사용한다. 아이템은 실제 검증된 보상 후보만 사용하고, 지급은 코디 자동 변경과 분리한다. 현재 의상 상품 0개로는 랜덤 코스튬 결과를 운영할 수 없다.

룰렛 출시 전 결정할 정책은 다음과 같다. 화면·상점 기본 연동은 이 결정과 독립적으로 진행할 수 있다.

- 6개 결과의 정확한 확률과 버전, 각 유료 자세의 50/70 카테고리.
- 랜덤 아이템 풀, 미보유 아이템 우선 여부, 이미 보유한 아이템·풀 소진 시 처리.
- 5/10일 달성 후 늦게 접속한 사용자의 미사용 티켓 누적·만료와 과거 달성 소급 여부.
- 최신 BE의 그룹 룰렛은 같은 개인 UserCurrency에 지급하며 물은 재화가 아니다. 개인 5일 스트릭 룰렛은 그룹 룰렛과 별도 자격·결과 정책으로 구현한다.

### 최신 BE 커밋 재점검 (2026-10-01)

최신 [f577481](https://github.com/r3j0/project-health/commit/f5774815fa7a42386672683fbf227a6e937ed0eb)의 제목은 `feat(backend): add group missions and reward roulette`이고 커밋 시각은 KST 2026-10-01 00:10:22다. 이전 조사 head에서 1커밋, backend 내부 27파일이 변경됐다. 원격 참조를 fetch하고 diff·문서·실제 호출 경로·DB 제약을 확인했다. FE 작업 브랜치에는 병합하지 않았다.

추가된 동작은 [그룹 미션 계약](https://github.com/r3j0/project-health/blob/f5774815fa7a42386672683fbf227a6e937ed0eb/backend/docs/group-missions.md)을 따른다.

- 그룹장이 최소 2명으로 회차를 시작하면 당시 참여자 N을 고정하고 목표를 누적 14N으로 저장한다. 성장 단계는 N/3N/7N/14N이다.
- 당일 전체 루틴의 최초 완료와 기존 유효 일별 배정 완료에서 사용자+KST 날짜 달성을 기록하고 자격 있는 진행 그룹에 자동 물 주기 1회를 반영한다. 운동 완료·날짜 달성·모든 그룹 기여가 같은 트랜잭션이다.
- 그룹 미션 완성 시 유효 참여자에게 `floor(개인 기여 / 7)`장의 그룹 룰렛권을 발급한다. 개인 연속 스트릭 5일 조건과 다르다.
- 그룹 룰렛 결과는 본인 1/3/5/7개(50/25/13/7%) 또는 원래 회차의 유효 기여자 각각 3/7개(4/1%)다. 그룹의 저장 정책을 사용하고 개인 룰렛 확률로 전용하지 않는다.
- 추첨·티켓 소비·수령자 명세·개인 재화 지급은 원자적으로 저장하고 같은 키 재시도는 저장 결과를 반환한다. 그룹 탈퇴·퇴출은 미사용 티켓 자격을 영구 무효화하지만 이미 받은 개인 재화는 회수하지 않는다.
- `grantCurrencyInTransaction`과 교착/직렬화 실패의 전체 트랜잭션 재시도 helper가 추가됐다. 기존 `grantCurrency` 호출 계약과 상점·코디 API는 유지한다.

새 API는 `/api/v1/groups/:groupId` 아래 `POST /missions/start`, `GET /missions/current`, `GET /missions`, `GET /roulette/tickets`, `POST /roulette/spins`, `GET /roulette/draws`다. 시작·추첨은 Idempotency-Key가 필요하고 추첨 body는 `{ticketId}`다. 추첨 응답은 지급 결과이며 현재 잔액은 포함하지 않으므로 FE는 성공 뒤 `/auth/me` 또는 avatar inventory를 재조회한다. 그룹 미션 화면 추가는 별도 그룹 작업 범위이며 현재 개인 상점 계획의 요구를 대체하지 않는다.

계속 남아 있는 개인 기능은 **하루 루틴 완료 직접 지급 1개, 개인 5일 배수 스트릭 룰렛, 랜덤 의상·자세 소유권 지급**이다. 의상 상품은 여전히 0개이고 임시 60개 자세도 그대로다. avatar 소유 획득 경로의 DB CHECK도 default/purchase만 허용한다. 새로운 `ActivityAchievement`와 트랜잭션 지급 helper를 활용하되 그룹 자격·기여 7회·확률표를 개인 규칙에 그대로 적용하지 않는다.

새 마이그레이션은 `20260930000400_group_missions`다. [검증 문서](https://github.com/r3j0/project-health/blob/f5774815fa7a42386672683fbf227a6e937ed0eb/backend/docs/group-missions-verification.md)는 단위·PostgreSQL 통합 475개·빌드 등 통과를 기록한다. 단위 건수는 본 검사 328개와 동시 미디어 변경을 포함한 332개 재검사를 별도로 기록하므로 정확한 커밋별 수치는 재실행으로 확인해야 한다. 이번 재점검은 읽기 전용 소스 조사이며 BE 검사 재실행·DB 적용·배포는 수행하지 않았다.

## 2026-10-01 FE 구현 범위 갱신

사용자 확정: **FE 구현 + BE 요청 규격만**, 영상 **80% 완료 유지**, 처방 수행은 선택. 기존 `/account/shop`·마이룸 계획 대신 하단 상점 `/shop`과 `/shop/wardrobe`를 연결했다. 그룹 미션/룰렛은 PR #9 계약을 사용한다. 자세 provisional 가격은 확정 전 구매를 차단한다.

현재 구현·추가 서버 계약·개인 룰렛 정책 공백·의상 상품 등록 제안·출시 설정은 [BACKEND-REQUESTS.md](BACKEND-REQUESTS.md)에 정리했다. 하루 지급/개인 룰렛은 BE 변경을 포함하지 않으며 출시 설정 기본값은 false다. 실제 지급 영수증이 없으면 씨앗/물 획득 화면을 주장하지 않는다.
